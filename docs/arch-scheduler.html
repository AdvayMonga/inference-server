Scheduler

The engine's heart. Decides which requests are batched together each tick, how to be fair across users, and how to refuse work cleanly when the system would otherwise melt.

The three queues

Every request sits in exactly one of these at any time.

Why a separate prefilling queue? Prefill is expensive but parallel-friendly across the prompt's tokens. Decode is cheap per token but happens many times. Mixing them in the same logical queue makes the scheduler harder to reason about. Keeping them separate means the chunked-prefill state machine can evolve without disturbing the decode batch.

What happens on a single tick

One iteration of the scheduler's worker thread, in order. The order matters — getting it wrong drops first tokens.

Preemption exists now, for KV pressure. The normal path is still a "soft hold" — a fitting request waits for room. But if a decode step fails because blocks ran out, the scheduler preempts the most recently admitted row rather than losing the batch (see Preemption & loop resilience). Preemption for strict priority classes or per-tenant SLAs is still deferred — see CLAUDE.md.

Chunked prefill

Long prompts no longer freeze every other user.

Version A (alternating, shipped): chunked prefill happens as a separate forward pass alongside the decode batch. Two passes per tick. Works on MPS today. Captures the latency win. Tested. Version B (mixed-batch, vLLM-style, deferred): a single forward pass packs decode rows and one prefill chunk together. Needs a custom attention path (FlashAttention varlen). CUDA-only. Pairs with the vLLM benchmark phase.
Prefill strategy is a config seam (PREFILL_MODE). monolithic (one forward on admit) or chunked (V-A) today; the enum is the forward-compat extension point for mixed_batch (V-B) and disaggregated (P/D) — all reuse the same _prefilling phase + prefill_chunk primitive. Empty config derives the mode from PREFILL_CHUNK_SIZE (back-compat: >0 → chunked); an unimplemented mode fails loud at construction.
The disaggregation seam: _promote_to_decode. Both monolithic admit and the chunked final-chunk path funnel a completed prefill's KV into the decode batch through this one method. Today it's a local splice on the same worker; under P/D disaggregation the KV is produced on a prefill worker and transferred here before the row decodes — so disagg adds a transfer at this single point plus a remote prefill loop, not a scheduler rewrite. The loop is already prefill/decode-decoupled, which is what makes that cheap.

Load shedding & the admission deadline

The gates above decide whether a request fits. They do not bound how long it waits, and a deep queue turns overload into unbounded latency rather than rejection.

Measured before this existed: at rate 48 the pending queue reached 1001 deep and end-to-end p95 hit 105 s while the engine reported almost no rejections — it looked healthy while being useless.

KnobEffect
MAX_QUEUE_WAIT_S (default 30)At admission, a request that has already queued longer than this is rejected with a queue-full error instead of admitted. 0 disables. Tune it to your TTFT SLO — a request that waited this long has blown any SLO it had.
MAX_QUEUE_SIZEHard cap on queue depth; rejects at enqueue time.

Preemption & loop resilience

Two things that decide whether a bad moment costs one request or the whole server.

  • Preemption under KV pressure. If a decode step fails while several rows are in flight, the scheduler evicts the most recently admitted row — freeing its blocks — and retries next tick. The newest request pays; older in-flight work survives. Counted as total_preempted.
  • The worker survives a failed iteration. It used to not: any exception escaped to _fail_all, which cleared the active batch without releasing its paged blocks and then let the worker thread exit — after which the server accepted requests forever and ran none of them, with the leaked blocks unrecoverable. Now a failed tick drops the in-flight work, releases its KV, and keeps serving; the worker only gives up after MAX_CONSECUTIVE_ERRORS failures in a row.

Prefill wave planning (optional)

A batched prefill right-pads every row to Smax, so a wave of mixed prompt lengths spends most of its compute on padding. WAVE_WINDOW_MULT lets the scheduler reorder within a bounded window to group similar lengths; the window head is always included, which is what makes it starvation-free.

Default 0 (off), because it is measured inert below saturation. The wave_sizes histogram in /scheduler/stats shows 83–91% of waves are K=1 at rates 1–6: the queue never backs up, so waves never widen and there is no padding to save. Turn it on when the engine is actually driven at its 100–256 concurrency target.

Do not read K=1 waves as a starved batch. At max_batch_size each completing request frees exactly one slot, so the next admission wave is K=1 by construction — a full batch at steady state produces the same histogram as an empty one. A sweep at 128 req/s with 2985 requests queued still showed 49% K=1, and that was read as starvation; the reading was withdrawn. wave_sizes measures prefill wave width, never occupancy. Use active_mean / active_high_water for occupancy.

Batch occupancy — the number that sets throughput

A decode step streams the entire weight matrix from HBM whether it serves one row or two hundred, so tokens/sec is decided by how many rows share that read. Sampled on every decode step and surfaced in /scheduler/stats:

FieldMeaning
active_meanMean rows per decode step. Compare to max_batch_size: a large gap alongside a deep pending_depth means admission is the constraint, not demand.
active_high_waterMost rows ever decoded together. Never exceeds max_batch_size — if it does, the admission gate leaked.
decode_stepsSample count behind the mean.
active_sizeInstantaneous len(). Fine for a live dashboard, useless for a benchmark: it is read after the run drains and reports 0.
Why these exist. Until they did, the engine's central question — how full was the batch — could not be answered from any recorded run. All 42 stored panels report active_size 0, and the research panel's concurrency_observed was being fed pending_high_water: queue depth, labelled as concurrency. It reported the opposite of what it claimed.

Reservation accounting (the load-bearing invariant)

The rule: _active_kv_reserved is the sum of (prompt_len + max_tokens) across every row in _active. Admit adds. Finish, evict, and any future preemption all subtract. If anything forgets to subtract, the engine starts hard-rejecting requests it could actually serve.
Mask bookkeeping rule: _splice_in sizes the attention-mask cat off the mask's own width (_attention_mask.shape[1]), not backend.kv_length(). For the paged custom backend kv_length = max(per-row len) drops when the longest row is evicted while the mask width doesn't — deriving the mask size from it cat'd mismatched widths and killed the worker (the 2026-06-12 mixed-workload crash). Scheduler-owned tensor state must be self-consistent, not derived from a backend metric whose invariants differ per backend.
