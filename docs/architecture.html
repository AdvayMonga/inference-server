How a single request flows through the system

Read this once and the rest of the diagrams will make sense.

  1. Client sends a POST to /generate with the prompt text, max tokens, optional session_id, and optional priority.
  2. Server tokenizes the text using the Gemma chat template and wraps it in a ScheduledRequest object that carries the session ID and arrival time.
  3. Scheduler queues the request. The fairness policy (FCFS or VTC) decides where it lands relative to other waiting requests.
  4. Each tick the scheduler tries to admit pending requests. It only admits if there's room in both the active-KV budget and the cache block pool. If not, the request waits — and if it has already waited past the admission deadline, it is rejected rather than queued forever.
  5. If the prompt is long, prefill is split into chunks, one chunk per tick — long prompts no longer freeze every other user's stream.
  6. The cache is checked for any matching prefix. If found, those tokens skip the forward pass entirely.
  7. The backend runs a single batched decode forward pass across every active request, producing one new token per request per tick.
  8. Each new token is streamed to its client via SSE. Metrics track TTFT and TPOT.
  9. When a request hits EOS or max tokens, it leaves the active batch, releases its blocks, and frees its KV reservation.

The research loop

The engine is the subject; the loop is how it changes. Method in LOOP.md, code in src/inference_server/research/.

LayerJob
Engine (src/inference_server/)Serve tokens. Knows nothing about the loop.
Instruments (scripts/)Know engine internals intimately. Emit a fixed vitals panel to runs/*.json via research.harness.
Loop (research/)Knows only the panel contract: attribute gaps, screen hypotheses cheapest-first, judge five gates, record. Engine-agnostic.
Procedure (research/session.py)Steps 4-6 as one call, so every iteration runs the same one. Refuses to judge before the gates even see the data if the arms are untagged, unbalanced, block-ordered, measured dirty, or stale. The library is the interface; the CLI is a shim over it, and premerge_check.py stays a script because it runs where no agent does.
Execution (research/venues.py)Runs one instrument on a rented GPU and brings the panel home: rent → rsync the working tree → run → parse a marked JSON block off stdout → terminate. Modal implements the same contract with a built image and a pickled return; the instrument does not know which it got. Teardown is in a finally on every path, including the ones that raise, because a pod bills until it is terminated. Needs RUNPOD_API_KEY.
Memory (knowledge/, experiments/)One JSON per record, git-tracked. DECISIONS.md is a generated view.

Five gates decide a merge, judged in this order: validity (did this harness exercise the change?) → sanity (did a metric this change cannot touch move anyway?) → significance (does it clear the variance budget on the metric predicted beforehand?) → correctness (fast suite green, no new iteration errors) → cost (undeclared startup or memory regressions fail). Validity is first because a confident number from a blind harness is worse than no number — this project shipped one for about a month.

The two gates that exist because they were missing. Sanity caught a CONFIRMED −48.2% produced by two arms that had run on different machines: they differed only in a prefill flag, yet TPOT p50 read 95.3 vs 46.4ms — and decode cannot move when only prefill changed. Replication exists because significance was reading the wrong variance: the panel's stderr is request-to-request scatter within one run, but this harness's run-to-run null spread is 3.2× on ttft_prefill_p95 and 6.5× on ttft_p95. One run per arm can never be significant, whatever the gap. Arms now need ≥3 runs each, first discarded as warmup (three identical back-to-back runs measured 1494 / 401 / 229ms — strictly decreasing), ordered ABBA so warmup cannot favour the arm that happens to go second.

scripts/premerge_check.py enforces that an engine change cannot reach main without a green experiment record. Two rules it also carries: an experiment vouches for the exact commit it measured, so if engine files changed after that sha the record is refused — never rebase after measuring — and a record with single-run arms cannot authorise a merge however green its gates look. Docs, tests, scripts and research/ itself are exempt; a gate that fires on documentation only teaches people to bypass it.

What happens when it runs out of memory

KV blocks are finite and running out is an expected operating condition, not a failure. The path, in order:

  1. Admission holds. A request whose reservation does not fit waits rather than starting (kv_admit_blocked).
  2. The prefix cache gives blocks back. The block pool calls into it before declaring exhaustion; cached prefixes are evicted LRU until a block actually frees.
  3. Preemption. If a decode step still fails, the most recently admitted row is evicted so older in-flight work survives.
  4. Rejection. Genuine exhaustion surfaces as a typed KVCacheExhausted converted to a 429-style rejection — never as an engine crash.
  5. Shedding. Requests that queued past the admission deadline are rejected, so overload becomes bounded latency plus refusals instead of unbounded latency.

Two invariants hold this together: no path may abandon blocks it has already allocated, and a failed scheduler tick must not end the worker — it drops the in-flight work, releases its KV, and keeps serving.
